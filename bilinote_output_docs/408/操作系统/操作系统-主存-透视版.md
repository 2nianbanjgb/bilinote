## 程序的生成与装入
[原片 @ 00:00](https://www.douyin.com/video/7607305862092295450)

一段包含主函数和加法函数的代码，是如何变成一个程序并加载到内存中由 CPU 执行的呢？

### 编译与链接
[原片 @ 00:09](https://www.douyin.com/video/7607305862092295450)

- **编译**：首先，编译器将源代码（如 `add` 函数和 `main` 函数）编译成目标模块（Target Module）。目标模块是由 0 和 1 组成的机器指令集合。
- **执行逻辑**：加法函数的核心部分是获取从堆栈传递进来的参数，然后执行加法指令。主函数也是同理。
- **链接**：两个源码被编译成两个目标模块。主模块通过 `CALL` 指令调用加法模块，但此时主模块并不知道加法模块的实际地址，因此地址处留空。链接器（Linker）将两个目标模块连接在一起，根据指令的偏移地址计算出加法函数的入口地址，用此地址将之前留空的位置填上。

### 静态链接与动态链接
[原片 @ 00:50](https://www.douyin.com/video/7607305862092295450)

- **静态链接**：在程序运行前就完成所有链接工作的方式（如在 Windows 下生成 `.exe` 文件）。这种方式会将所有模块（包括标准库）拼接到一起，如果程序使用了很多模块，可执行程序会变得特别大。
- **动态链接库（DLL）**：将常用模块打包成动态链接库（本质是二进制程序）。
  - **装入时动态链接**：在操作系统将程序装入内存时，动态地将主程序和动态链接库链接在一起。
  - **运行时动态链接**：只装入主程序，其他部分在程序需要用到时才链接进来，节省内存。

### 内存分配与空闲分区表
[原片 @ 01:43](https://www.douyin.com/video/7607305862092295450)

内存就像一卷带有格子的纸带，行索引就是内存地址。内存分配就是从纸带上剪下一小块给进程使用，当另一个进程申请时，继续从剩下的内存剪下一小块给它，**释放时**则归还。

![](./操作系统-主存-透视版/screenshot_020_eb55f625-cd79-4b93-83db-0ed8971a0b58.jpg)
![](./操作系统-主存-透视版/screenshot_021_5c83f6d6-62d4-44f1-a0fb-75895550f3ab.jpg)
![](./操作系统-主存-透视版/screenshot_022_4643c6b7-eb1e-4c8e-99df-e0e8e2bce52c.jpg)
![](./操作系统-主存-透视版/screenshot_023_f003db90-6037-420b-bd75-68a0ae0432f1.jpg)

当内存块不连续时，可以使用**空闲分区表**来管理。表格记录着每一块内存片段的起始地址、分区大小和状态（如有效/无效）。
- **分配**：从表中遍历找到合适大小的内存块。若申请内存小于分区大小，可进行**剪开**按需分配，并修改表中的信息。
- **释放**：将对应的信息写入表中，标记为空闲。

### 空闲分区链与内存碎片合并
[原片 @ 02:53](https://www.douyin.com/video/7607305862092295450)

随着内存块被切得越来越碎，空闲分区表会占用大量空间。因此，可以通过**链表**来实现管理。

- **数据结构**：一个内存块的头部记录当前块的大小和分配状态位。将头部信息原封不动地复制到尾部，用作**边界标记**。
- **分配**：按需剪下内存块，更新头部和尾部的信息。头尾记录的大小包含头尾本身，实际分配给进程的是中间部分。若需分配大小，需加上边界标记的大小。
- **双向链表组织**：释放的内存块插入链表的头部。为了找到空闲内存块的入口，用一个变量保存空闲内存块的起始地址（入口）。为了将空闲块组织起来，块内记录上一块和下一块的地址。

- **合并机制**：内存块被切得过分细碎会导致无大块可用。因此需要合并相邻的空闲内存块。
  - 通过当前地址减去偏移量找到物理上相邻的上一个内存块的尾部，判断是否空闲。
  - 通过当前地址加上当前大小找到物理上相邻的下一个内存块的头部，判断是否空闲。
  - 若空闲，则将**相邻内存块**从链表中摘出，擦掉中间信息，重建头尾，然后放回链表头部。
  - **合并机制触发 = 物理地址相邻 ∧ 双方都空闲 ∧ 分配器策略允许（同区域/同类/未被延迟）**

## 动态分区分配算法
[原片 @ 05:30](https://www.douyin.com/video/7607305862092295450)

在不断的剪裁与合并中，内存块大小不一。假设进程申请 1.5M 内存，应该分配哪一块？由此引出了不同的分配算法。

![](./操作系统-主存-透视版/screenshot_055_d7f829e0-0558-40e5-8990-31d1cb945617.jpg)

### 首次适应算法（First Fit）
[原片 @ 05:36](https://www.douyin.com/video/7607305862092295450)

- **原理**：按地址升序排序，从头开始遍历，找到第一个大小合适的空闲块进行分配。
- **缺点**：总是从低地址开始扫描，导致低地址空间被频繁划分，内存前半部分的大块被剪得稀碎，每次分配都需要跳过一堆碎片，查询开销增加。

![](./操作系统-主存-透视版/screenshot_056_19909b9d-2e8f-4ceb-9d68-cfec136e3910.jpg)
![](./操作系统-主存-透视版/screenshot_057_53a375f3-7565-4ba5-9c73-b62fbf301de6.jpg)
![](./操作系统-主存-透视版/screenshot_058_f0cafa7e-d593-4c68-bed6-cf39c7cb8869.jpg)
![](./操作系统-主存-透视版/screenshot_059_bee590d4-a6a0-47cc-bb12-00d703fcb59d.jpg)

### 最佳适应算法（Best Fit）
[原片 @ 05:58](https://www.douyin.com/video/7607305862092295450)

- **原理**：按内存块大小从小到大排序。优先匹配大小合适的小块，以避免大块被破坏。
- **缺点**：内存块和申请大小过于接近时，会剪下极小的一丝（外部碎片），后续任何进程都看不上，导致很多碎片垃圾。

![](./操作系统-主存-透视版/screenshot_060_cd3103e5-cba7-4bc4-ae06-2d607f856353.jpg)
![](./操作系统-主存-透视版/screenshot_061_670c6626-2fc9-49a7-b85a-4f24b1138fa0.jpg)

### 最坏适应算法（Worst Fit）
[原片 @ 06:15](https://www.douyin.com/video/7607305862092295450)

- **原理**：按内存块大小从大到小排序。优先从最大块那里剪裁，剩下的大块仍然是大块，避免了碎片垃圾，查询效率也高。
- **缺点**：大块很快会被耗尽，导致后续无大块可用。

![](./操作系统-主存-透视版/screenshot_062_44d56c2c-2aeb-4fe3-babe-c3cca303d09d.jpg)
![](./操作系统-主存-透视版/screenshot_063_ee6244c4-4742-40a0-8807-844524faa491.jpg)

### 邻近适应算法（Next Fit）
[原片 @ 06:31](https://www.douyin.com/video/7607305862092295450)

- **原理**：按地址升序排序，具备首次适应算法的特性，但记录下上一次分配结束的位置，下次分配从该位置继续查找。查询到链表尾部则从头开始循环。
- **缺点**：会导致内存块均衡地被“剪烂”，实际性能甚至不如首次适应算法。

![](./操作系统-主存-透视版/screenshot_066_0df04bc2-5fae-4bce-89d5-2cd0cd4aa1d7.jpg)
![](./操作系统-主存-透视版/screenshot_067_861a8915-2677-4e18-ba5b-6ead7a836e53.jpg)
![](./操作系统-主存-透视版/screenshot_068_821963f7-bdd9-4126-9494-841994231cdd.jpg)

### 快速适应算法（Quick Fit）
[原片 @ 06:50](https://www.douyin.com/video/7607305862092295450)

为了解决线性查询的性能瓶颈，可以根据内存块大小进行分类（如 2K, 4K, 6K 等），每个分类有独立的链表。释放的内存直接挂回对应的链表，不需要合并。对于大内存空间，可以划分区间进行管理（如 1M~128M 划为一类）。

- **特点**：这种查询方式称作**哈希搜索 (对于大内存空间，可以划分区间进行管理，内部再用上述分配适应算法)**。但对于海量内存，分类数量依然很大，且依赖人工划分，缺乏灵活性。

## 伙伴系统
[原片 @ 07:38](https://www.douyin.com/video/7607305862092295450)

伙伴系统（Buddy System）就像掰巧克力的过程，是操作系统常用的内存分配算法。

![](./操作系统-主存-透视版/screenshot_076_528e1515-1eba-4ff2-ae81-a3467cb4f12b.jpg)
![](./操作系统-主存-透视版/screenshot_077_97ef61b8-7c66-44b9-a82d-abd7c772c0de.jpg)
![](./操作系统-主存-透视版/screenshot_078_c56e0224-6b85-449d-a74f-969885c7030c.jpg)

- **分配机制**：内存分类大小为 4K, 8K, 16K, 32K 等（必须是 2 的幂次）。若申请 4K 内存，发现缺失，则向更高等级申请，直到 32K 有内存。将 32K 一分为二成两个 16K，放一个到 16K 分类，另一个再一分为二成两个 8K……不断递归拆分直到得到 4K 分配给进程。
- **释放机制**：内存块释放时，检查其“伙伴”是否空闲。若空闲，则合并成更大的块，递归往上归还。**伙伴**指的是能完整拼成一个大块的两个**相邻**内存块。

### 段式存储管理（Segmentation）
[原片 @ 10:04](https://www.douyin.com/video/7607305862092295450)

**核心思想**：将**程序**逻辑空间划分为多个逻辑单元（分段），如数据段、代码段。需要开发者手动将代码划分成不同的段。

**注意，here 裁的是程序的逻辑空间，不是内存空间，柜子塞不下剪衣服**

![image-20261108023951540](./操作系统-主存-透视版.assets/image-20261108023951540.png)

![](./操作系统-主存-透视版/screenshot_100_e356dc06-6178-44d6-8816-fa1b78f560bb.jpg)
![](./操作系统-主存-透视版/screenshot_101_1457e311-108f-498b-a130-4d1f1c0e1f5a.jpg)
![](./操作系统-主存-透视版/screenshot_102_f825c22e-99b7-4499-93b6-7d270be276c1.jpg)

- **段表**：记录段号对应的段长（Limit）和基址（Base）。基址是分配的内存块起始地址，段长指的是这块内存空间的大小。

- **寻址过程**：逻辑地址由段号和段内地址组成。逻辑段内地址加上基址，即可得出物理地址。

  ```python
  CPU 生成逻辑地址 (段号, 段内地址)
          │
          │ ① 用段号查段表，取出该段的基址（和段长）
          ▼
     基址 + 段内地址
          │
          │ ② 越界检查：段内地址 < 段长？
          ▼
     物理地址 = 基址 + 段内地址
          │
          ▼
     送到内存总线，访问真实内存单元
  ```

![](./操作系统-主存-透视版/screenshot_104_c677dd0b-0631-4109-b99a-98548c29a509.jpg)
![](./操作系统-主存-透视版/screenshot_105_be17f500-7c7a-4332-8e1a-54a2420e655d.jpg)

- **缺点**：单个逻辑段仍然需要连续的内存空间分配，若内存碎片过多，仍无法利用。

### 页式存储管理（Paging）
[原片 @ 10:49](https://www.douyin.com/video/7607305862092295450)

**核心思想**：将逻辑空间和物理空间都裁剪成相同大小的页（通常为 4K）。逻辑页映射到物理页，更充分地利用碎片。

![](./操作系统-主存-透视版/screenshot_108_013a00a3-e937-42eb-a5f1-6b212f466768.jpg)
![](./操作系统-主存-透视版/screenshot_109_674329a8-a056-4ee1-b864-3b193e1ebef0.jpg)
![](./操作系统-主存-透视版/screenshot_110_5eb5b21e-1cca-46e0-b2c4-158fabd23166.jpg)

- **页表**：记录逻辑页号到物理页号的映射关系。
- **寻址过程**：物理页的基址可通过物理页号乘以 4K 得出。逻辑页内地址加上对应物理页的基址，得出物理地址。在二进制中，4K 正好是 12 位，因此逻辑地址的低 12 位是页内地址，剩余高位是逻辑页号。
- **机制**：物理页号拼接上页内地址即可得出物理地址。这个寻址过程由**内存管理单元 (MMU)** 和操作系统共同完成，开发者无感。

- **对比**：
  - **段式存储**：开发者知道代码被分成两段，需要显式指定段和段内地址。地址是二维逻辑地址。方便进行**共享和保护**。

- **地址结构**：逻辑地址由**段号 + 逻辑页号 + 页内地址**三部分组成。通过段号和逻辑页号查出物理页号，拼接页内地址得出物理地址。

### 页面置换算法
[原片 @ 14:46](https://www.douyin.com/video/7607305862092295450)

当内存满是，应该淘汰哪个页面？

- **先进先出算法（FIFO）**：根据装入先后顺序，谁先装入就先淘汰谁。
- **最久未使用算法（LRU）**：记录访问时间，淘汰时间值最小的页面。每次置换都需要遍历排序，开销大。
- **时钟置换算法（Clock）**：改进 LRU。用一个比特的访问位记录，访问过的页面访问位设为 1。系统循环检查每个页面，若访问位为 1 则重置为 0（类似扫帚或一对多的围棋，有新访问可以从0又变为1，但如果一圈了还没新访问，就淘汰掉）；直到遇到访问位为 0 的页面（说明一轮内未被访问），则淘汰它。
- **改进型时钟算法**：结合访问位和修改位，分成四个优先级：优先淘汰未访问未修改的，其次淘汰未访问已修改的，第三淘汰访问过未修改的，最后淘汰访问过已修改的。避免淘汰脏页（需写回硬盘）。
- **最佳置换算法（OPT）**：淘汰未来最长时间不再被访问的页面。由于未来不可测，无法实现，但可作为衡量标准。

### 驻留集与内存分配策略
[原片 @ 16:15](https://www.douyin.com/video/7607305862092295450)

系统运行时多个进程竞争有限的内存页，应该如何分配？

- **平均分配算法**：把物理页平均分配给进程。大程序和小程序分到相同页数，对前者不公平。

- **按比例分配算法**：根据进程逻辑大小分配。设进程逻辑大小为 $s_i$，所有进程逻辑大小总和为 $S$，内存物理页数为 $m$，则可获得的页面数 $S_i = \frac{s_i}{S} \times m$。

- **工作集与驻留集**：程序逻辑页数多并不意味着需要很多内存（如 5MB 的超级玛丽和 2GB 的游戏）。已分配给进程的物理页称为**驻留集**，某个时间段内实际访问的页面集合称为**工作集**。理想状态下，驻留集 $\approx$​ 工作集。

  ```python
  程序执行具有时间局部性和空间局部性：
  同一时刻，CPU 只在少数代码段和数据段上反复执行。一个 2GB 的游戏，其代码和数据可能分布在成千上万个页面里，但某一帧渲染时真正被访问的，可能只是当前关卡的地图、当前角色的模型、当前播放的音频等少数页面。其余页面（其他关卡、未触发的剧情、备用资源）虽然存在于逻辑地址空间中，但当前并不活跃，完全可以留在磁盘上，需要时再调入。
  
  因此，"逻辑页数多"只说明虚拟地址空间大，不说明"同时需要驻留的页多"。
  ```

- **按优先权分配算法**：根据进程权重分配页面。

### 页面置换策略与快表机制
[原片 @ 17:36](https://www.douyin.com/video/7607305862092295450)

多个进程同时运行时，进程驻留集满时，需要置换页面。

```python
# 页面置换：
当物理内存（或分配给某进程的驻留集）已经装满、又发生缺页中断需要调入新页面时，操作系统必须从内存中选出一个已有的页面“请出去”，腾出物理页框给新页面使用。这个“选谁出去”的过程就叫页面置换。

# 缺页中断：
CPU 访问一个虚拟页面时，硬件检查页表发现该页不在物理内存中（页表项的有效位为 0），于是触发一个中断，把控制权交给操作系统，由操作系统负责把该页从磁盘调入内存。它不是程序错误，而是虚拟内存按需调页机制的正常组成部分。
```

- **置换策略分类**：
  - **固定分配 + 局部置换**：驻留集不变，只从自己拥有的页面中换出。
  - **可变分配 + 局部置换**：驻留集可变化，但只从自己的页面换出。
  - **可变分配 + 全局置换**：不仅换出自己的，还能剥夺其他进程的驻留集页面，并加入当前进程的驻留集。不存在“固定分配+全局置换”。

- **页面缓冲机制（性能优化）**：置换的如果是脏页，就需要复制到交换区，就会产生一次硬盘 I/O 操作，容易产生性能问题。因此建立两个链表：**修改（脏）页面链表**和**空闲页面链表**。
  - 脏页换出时不直接写硬盘，而是先放入脏页链表，然后立马从空闲链表取出一个给进程使用。
  - 当脏页链表累计到一定数量时，再统一批处理写入硬盘（交换区），减少 I/O 次数。写入（交换区）后，脏页面（从脏页链表离开）再写入空闲页面链表。
  - 当空闲链表没有存货（即，无可用的物理页框）时，如果进程此时申请或者置换，会造成阻塞。因此引入**回收守护进程**，在空闲页面低于警戒线时，主动将页面回收，保证空闲页面（可用的物理页框）有一定存量。
